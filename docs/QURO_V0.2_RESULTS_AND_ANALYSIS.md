# QuRO v0.2 实验结果与分析

> 日期：2026-09-16
> 原始数据：[`results/xi_off_sweep.json`](../results/xi_off_sweep.json)
> 实施记录：[`QURO_V0.1_IMPLEMENTATION_PLAN.md`](QURO_V0.1_IMPLEMENTATION_PLAN.md) §10.5–§10.8
> 状态：**机制已证实（§7），定位待重建（§8）**。原主张「query 条件读出更准」在 D0 下不成立，但 readout 确实携带 query 信息（p=1.8e-96）

---

## 0. 一句话结论

**readout 确实能做 query 条件选择（D1 下比 query 无关版高 20.85 个 EM 点，p=1.8e-96），但在标准设定下这个能力是冗余的**——7B decoder 拿到问题明文后自己就完成了证据匹配。

所以问题不是「方法能不能工作」，而是「**在什么条件下这个能力不再冗余**」。这是定位问题，不是可行性问题。

同时 §8 纠正了本文档早先版本的一个报告错误：把 arm P 当作同工作点的天花板是错的，**P 在 16× 压缩下运行而 C 在 88× 下**，两者不在同一个点上。

## 1. 实验设置

| 项 | 取值 |
|---|---|
| 评测集 | TriviaQA eval，2000 条，每条 1~2 篇 gold + 4 篇随机干扰（noisy top-k 设定） |
| 生成器 | Mistral-7B-Instruct-v0.2 + LoRA，从各自压缩器的 adapter 热启动 |
| decoder 输入 | **D0**：系统指令 + `Background:[B 个 soft token]` + `Question: 问题明文` |
| 预算 | B = 8（`budget_buckets=[4,8]`，budget dropout） |
| 训练 | 3000 步，98k 条 SeleCom 数据，答案 CE |
| 检验 | McNemar 精确检验，逐题配对 |

### 四个 arm 的定义

| arm | 送进 decoder 的 soft token | 做什么 | 看 query 吗 | 可训参数 |
|---|---:|---|---|---:|
| **P** pisco_direct | 175（m=32）/ 44（m=8） | **不做二次压缩**，缓存 latent 原样全喂 | 否 | 0 |
| **A** agnostic | 8 | 完整 QuRO readout，把 175 个 latent 压成 8 个 | **否** | 33.7M |
| **C** ours | 8 | **同一架构、同样训练**，唯一区别是 output query 注入了 query | **是** | 33.7M |
| **S** similarity | 8 | 余弦 top-B，逐行原样取 latent | 是 | **0** |

**A 是关键对照**：它和 C 唯一的差别就是「读出时看不看问题」，所以 `C − A` 精确地量出 query 条件化的价值。P 不是竞争对手，是天花板参照（"不压缩能拿多少"）。

## 2. 结果

### 2.1 m = 8（PISCO 原生，K·m/B = 5）

| arm | soft token | prefill | substring | EM | F1 |
|---|---:|---:|---:|---:|---:|
| P 不压缩 | 43.8 | 111 | **77.20%** | 70.75% | 0.770 |
| S 余弦 top-B | 8 | 71 | 76.10% | **71.70%** | 0.765 |
| C ours | 8 | 71 | 76.00% | 70.90% | 0.762 |

`C vs S`：substring −2 净（p=0.94），EM −16 净（p=0.32）→ **完全打平**。

### 2.2 m = 32，两条互相独立的路线（K·m/B = 40）

两条路线的混淆变量不同——COCOM 换了整套 checkpoint，切块丢失跨块上下文——所以**绝对数值不可跨栈比较**（证据增益 P 臂 +9.80 vs +6.95 即为证），可比的只有**结论**。

**切块-PISCO 栈**

| arm | soft token | substring | EM | F1 | 错配文档 | 证据增益 |
|---|---:|---:|---:|---:|---:|---:|
| P 不压缩 | 175.4 | **78.90%** | **71.20%** | 0.778 | 69.10% | +9.80 |
| A 不看 query | 8 | 73.90% | 69.00% | 0.745 | 67.55% | +6.35 |
| C ours | 8 | 73.70% | 68.55% | 0.740 | 67.30% | +6.40 |
| S 余弦 top-B | 8 | 73.40% | 69.15% | 0.742 | 67.95% | +5.45 |

**COCOM 栈**

| arm | substring | EM | F1 | 错配文档 | 证据增益 |
|---|---:|---:|---:|---:|---:|
| P 不压缩 | **77.05%** | 67.10% | 0.762 | 70.10% | +6.95 |
| A 不看 query | 73.80% | **68.95%** | 0.748 | 68.40% | +5.40 |
| C ours | 73.50% | 66.10% | 0.738 | 68.30% | +5.20 |
| S 余弦 top-B | 73.85% | 66.05% | 0.738 | 69.15% | +4.70 |

> COCOM 栈有个反常处：A 的 EM（68.95%）高于不压缩的 P（67.10%）。175 个 COCOM latent 的 prompt 长度对 COCOM 的 decoder 是 off-distribution。

### 2.3 配对检验（两栈逐条一致）

| 对比 | 切块-PISCO 栈 | COCOM 栈 |
|---|---|---|
| C vs S | +6 sub (p=0.74) / −12 EM (p=0.50) | −7 sub (p=0.69) / +1 EM (p=1.00) |
| **C vs A（query 条件效应）** | −4 sub (p=0.84) / −9 EM (p=0.60) | −6 sub (p=0.73) / **−57 EM (p=0.0007)** |
| P vs C（压缩的代价） | **+104 sub (p<0.0001)** | **+71 sub (p<0.0001)** |

COCOM 栈里 A 在 EM 上**显著优于** C；substring 无差异，两指标不一致故只能报「无可靠差异」，但方向为负。

## 3. 分析

### 3.1 把效应拆成三段

```
闭卷（不给证据）      62.40%   ← n=500，同一 decoder
   │
   ├─ 证据本身值多少 ──────────────► 检索的价值，不是我们的贡献
   │
给全部证据 P          78.90%
   │
   ├─ 压缩 175→8 的代价 ──────────► 5.2 分，p<0.0001   ← 真实且显著
   │
给 8 个 token         73.70%
   │
   └─ 怎么挑这 8 个 ──────────────► 0.5 分以内，p>0.6  ← 我们的创新点在这
       C（学+看query） 73.70%
       A（学+不看）    73.90%
       S（0 参数余弦） 73.40%
```

**三个架构差异极大的 readout 落在 0.5 分以内，而「压不压缩」值 5~7 分。损失发生在「175 → 8」这个动作本身，与「怎么挑这 8 个」无关。**

### 3.2 成立的部分

**压缩效率是真实的**。m=8 时 8 个 soft token（71 prefill）相对 44 个（111 prefill），只掉 1.2 分 substring；m=32 时 8 个相对 175 个，掉 5.2 分。按「每多花一个 prefill token 换多少证据增益」算，8-token 方案是 PISCO 的 2.2 倍、未压缩全文的 17 倍。

**但这段效率来自「压缩」，不来自「query 条件化」**——A 和 S 同样拿得到。

### 3.3 不成立的部分

| 原主张 | 状态 | 证据 |
|---|---|---|
| 离线 query 无关压缩可缓存复用 | 成立 | 但这是 PISCO/COCOM 已有的，非本工作贡献 |
| 在线用 query 做条件读出 | **未实现** | C ≈ A，两栈 p=0.84 / 0.73 |
| 读出优于 query 无关的二次压缩 | **否定** | 同上；COCOM 栈 EM 上 A 显著更优 |
| 读出优于非参数基线 | **否定** | C ≈ S，两栈一致 |

### 3.4 可证伪预测被推翻

§10.5.4 预注册了「收益随 K·m/B 单调增长」：

| 配置 | K·m/B | C − S (substring) |
|---|---:|---:|
| m=8 (PISCO) | 5 | −0.10 |
| m=32 (切块) | 40 | +0.30 |
| m=32 (COCOM) | 40 | −0.35 |

**压缩比放大 8 倍，两条独立路线均无收益。预测在它自己指定的位置被否定。**

## 4. 方法学副产品（与主张无关，但值得单独记录）

这些是本轮踩出来的坑，对任何 RAG 压缩工作都适用：

1. **必须有无证据下界。** TriviaQA 上整条检索压缩链路只值 3.8~12 分，其余是模型闭卷知识。不报这条线，arm 之间的差距无法解释。
2. **必须有常量答案地板。** SeleCom dev 43% 是非题，常量输出 "Yes" 就有 6.75% EM。
3. **跨格式基线不能用 EM。** plain Mistral 与 PISCO-adapted decoder 闭卷能力相同（63.2% vs 62.4% substring），EM 却差 280 倍——差的是啰嗦程度，不是正确率。
4. **小样本先抛点估计会骗人。** n=500 时 C 领先 S 1.6 分，n=2000 时 99 胜 101 负。检验必须先于结论。
5. **形状/NaN 校验抓不住错误的*映射*。** 缓存合并 bug 让一半文档返回别人的 latent，所有既有校验全部通过，是**错配文档对照**把它抓出来的。没有它，会得出「m=32 没有收益」这个与事实相反的结论。
6. **因果模型下 mem token 的位置不是格式问题。** COCOM 代码把它前置，导致所有文档压出同一个常数向量（文档间距离实测 0.0）。判定必须来自实测。

## 5. 三项尚未测试的条件

写下本节时它们都是未知数。**第一项已完成且结论为正（§7）**，另两项仍待补。

### 5.1 D1 / query 明文 dropout —— 已完成，结果见 §7（假设被证实）

D0 模式下**问题明文就在 prompt 里**，而 decoder 是个 7B 模型，「问题↔证据」匹配它自己就做得很好。**readout 的 query 条件化与它完全冗余。** `DecoderInputConfig` 的注释里写明了 D1 存在的理由，`scripts/run_gonogo.sh 2` 也写好了，但一次都没跑。

**`C ≈ A` 完全可能只意味着「D0 下无需如此」，而非「readout 做不到」。** 这是最相关也最便宜的一项。

判据：
- D1 下 **C 显著超过 A** → 机制有效，D0 掩盖了它，idea 活着
- D1 下 **C 仍 ≈ A** → readout 确实无法携带 query 信息，idea 证伪

**已于 2026-09-16 完成，结论为前者：D1 下 C 比 A 高 20.85 个 EM 点，p=1.8e-96。详见 §7。**

### 5.2 只测了 B = 8 一个点

整个方法的前提是「预算受限的读出」，我们只看了一个预算。`budget_buckets=[4,8,16,32]` 一次训练可给出四个点，看 C 能否随 B 增大逼近 P。这条曲线决定要不要改架构。

### 5.3 测试床没有判别空间

TriviaQA 闭卷 62.4%、未压缩全文 74.6%，**整个证据通道只有 12.2 分**。n=2000 时可靠分辨约 2 分，即**可用空间的 16%**——一个真实但温和的效应完全可能藏在噪声里。

更关键的是：**TriviaQA 以单事实问答为主，根本不需要 B 个槽位分工**，而多槽位分工正是本架构相对重排序的卖点。这是对我们最不利的设定。

可用替代：`/home/lxy/selecom/data/nq/dev/`（7 分片 ≈ 7800 条 Natural Questions，原始 Google 格式，需转换）。优点是闭卷正确率远低于 TriviaQA，且**同一篇维基的其他段落天然是主题相关的硬负例**。此外应寻找多跳数据集——只有「答案需要多个不同事实」时，槽位分工才有意义。

## 7. D1 实验：readout 确实能携带 query 信息（2026-09-16）

### 7.1 设置

四个 arm，m=8 PISCO 原生缓存，TriviaQA 全量 2000 条，D0 与 D1 两种模式各评一次：

| arm | 训练时看到问题明文的比例 |
|---|---|
| `d1_C_full` / `d1_A_full` | **0%**（`--query_text_dropout 1.0`，最强逼迫） |
| `d1_C_half` / `d1_A_half` | 50%（`0.5`） |

C 与 A 同架构、同参数量、同训练，唯一差别是 output query 里有没有注入 query。D1 评测把问题明文从 prompt 里整段拿掉，**soft token 成为 query 信息的唯一通道**。

### 7.2 D1 评测结果

| qdrop=1.0 | EM | substring | F1 |
|---|---:|---:|---:|
| **C（看 query）** | **26.75%** | **29.35%** | **0.327** |
| A（不看） | 5.90% | 12.65% | 0.114 |
| 地板（错配文档） | 0.35% | 0.70% | 0.015 |
| **C − A** | **+20.85** | **+16.70** | **+0.213** |

配对检验：EM **447 胜 / 30 负，p = 1.85e-96**；substring 431/97，p = 3.11e-51；F1 t = +21.6。三指标方向一致、全部极显著。

qdrop=0.5 同向：C − A 为 EM +16.05（p=1.2e-66）、substring +12.55（p=1.1e-32）。

**§5.1 的假设被证实：`C ≈ A` 意味着「D0 下不需要」，而非「readout 做不到」。** readout 完全有能力做 query 条件选择，差距是 4.5 倍。

### 7.3 但 D0 下效应仍然消失

| | C − A (EM) | C − A (substring) | 判定 |
|---|---:|---:|---|
| qdrop=1.0 | +3.10 (p=5.7e-5) | +0.45 (p=0.58) | 指标不一致 |
| qdrop=0.5 | +0.60 (p=0.45) | +0.25 (p=0.78) | **无差异** |

且 **D1 的绝对分数远低于 D0**（26.75% vs 68.20%）：拿掉问题明文要付 41 分，而 prefill 只从 71 降到 52。**这个交易本身不划算**，D1 不是一个实用设定，它是一个诊断工具。

### 7.4 结论的准确表述

> **能力已被证实，但在标准设定下它是冗余的。** 7B 的 decoder 拿到问题明文后自己就能完成证据匹配，readout 的 query 条件化与之重复。

这把问题从「方法能不能工作」转成了「**在什么条件下这个能力不再冗余**」——一个定位问题，而非可行性问题。

### 7.5 由此得到的锐利预测

§3.1 的「损失在 175→8，不在挑哪 8 个」是 **B=8 下**的结论。现在既然确认"挑哪 8 个"携带 query 信息，那么合理的解释是：**B=8 的预算足够宽松，任意 8 个配上问题明文都够 decoder 还原答案。**

由此：

> **C − A 应随 B 减小而单调增大，在 B→1 时最大。** B=1 时只剩一个向量，decoder 无从补偿，"留哪个事实"必须由 query 决定。

这是 §5.2 的 B 扫描，但现在带有方向性预言而非「看看曲线」。`budget_buckets=[1,2,4,8,16]` 一次训练给出五个点。**若 C−A 在小 B 处不增大，则「冗余论」被推翻，需另寻解释。**

## 8. 定位讨论：和谁比、比什么（2026-09-16）

本节修正本文档早先版本的一个报告错误，并重建方法的定位。

### 8.1 纠正：P 和 C 不在同一个压缩率上

| arm | soft token | **ξ_eff** | substring | EM |
|---|---:|---:|---:|---:|
| C (ours) | 8 | **87.65×** | 76.00% | **70.90%** |
| P (PISCO) | 43.8 | **15.99×** | 77.20% | **70.75%** |

§3.1 把 P 当作「天花板」、把 `P − C = 5.2 分` 说成「压缩的代价」——**这个框架是错的**。P 在 16× 压缩下运行，C 在 88× 下，两者是压缩-质量曲线上的两个点，不是同一工作点的上下限。

正确表述：

> **QuRO 在 88× 压缩下，EM 与 PISCO 在 16× 压缩下持平（70.90 vs 70.75），substring 低 1.2 分。**

而 SeleCom 论文的默认压缩率是 **82×**（`article/SELECOM_PAPER_NOTES.md` §5），**我们正好在同一个工作点上**。

**但这只是纠正报告方式，不产生任何新证据。** 实验数据一分未变，且 A 与 S 同样达到 88×——所以这段效率来自「两段式压缩」，仍然不来自「query 条件化」。

### 8.2 缺失的关键基线：同压缩率的一段式压缩

SeleCom 的核心论断是「**在极高压缩率下，query-conditioned selection 明显优于 query-agnostic full compression**」。注意它的对照物：**同样压到 82× 的 query 无关压缩**。

PISCO/COCOM 要达到 82×，只能靠**离线极端压缩**——COCOM rate 128 给出 m=1，K≈5.5 篇即 5.5 个 token ≈ 122×。

**而我们的 arm A 不是那个东西。** A 是「离线宽松压（m=8，16×）→ 在线学出来的池化到 8 个」的**两段式**结构，起点远好于一次性压到 82×。

| | 离线 | 在线 | ξ_eff | 已跑 |
|---|---|---|---:|---|
| P | PISCO 16× | 不压 | 16× | ✅ |
| C / A / S | PISCO 16× | 压到 B=8 | **88×** | ✅ |
| **COCOM-128** | **一次压到 122×** | 不压 | 122× | ❌ |
| SeleCom | 无（不可缓存） | query 条件压 | 82× | ❌ |

**「同为 ~82×，两段式 vs 一段式」这个对比从未做过。** 若 COCOM-128 明显差于 A，则「宽松离线 + 激进在线」的两段式结构本身即是贡献，与 query 条件化无关。

### 8.3 一个可检验的假说，解释 C ≈ A

SeleCom 在 82× 观察到 query 条件化的明显收益，我们在 88× 没有。自洽的解释：

> **SeleCom 的 query 无关基线（一段式压到 82×）很弱，留给 query 条件化的空间很大；我们的 A（两段式）已经很强，空间被吃掉了。**

即：**我们可能已经用「两段式结构」拿到了 SeleCom 用「query 条件化」拿到的那部分收益，只是归因给了错误的机制。**

这不是自我安慰，是可证伪的：跑 COCOM-128 即可验证。

### 8.4 结构性差异在哪

| | 离线（每篇文档一次） | 在线（每个 query 一次） | 可缓存 | B 可调 |
|---|---|---|---|---|
| PISCO | 压缩 → m 个 latent | 喂 K·m 个 latent | ✅ | ❌ m 被训练过的 `<MEM0..7>` 钉死 |
| SeleCom | **无法预先做** | **对 K 篇各跑一次 7B 压缩器** | ❌ | — |
| **QuRO** | 压缩 → m 个 latent | 40M readout 一次 | ✅ | ✅ **服务时任意 B** |

**QuRO 唯一结构性独占的性质是：在线证据预算 B 与离线压缩率解耦。** 一份缓存服务任意 B——budget dropout 已实现，单个 checkpoint 同时服务 B=4 与 B=8。这正是 `QURO_EXPERIMENTAL_DESIGN.md` §5 把摊薄曲线称为「别人做不出来的图」的原因。

### 8.5 关于「中间模块初始化很烂」的结构性顾虑

顾虑成立：PISCO/SeleCom 的中间环节是 7B 模型端到端训出来的，QuRO 塞进一个 40M 的随机初始化模块。

但实测表明**这个问题主要不是容量问题，而是初始化问题，且已大部解决**：余弦先验把初始化点从 47.00% 提到 65.00%，而旧初始化**比完全不给证据还差 15.4 分**（§7 之前的测量）——那才是「成绩很烂」的真正原因。

更根本的是分工：**readout 不需要与 7B 压缩器竞争。** PISCO 的 7B 压缩器做「原文 → latent」的重活，我们复用；readout 只做「latent → latent 子集」的轻活，搜索空间本就不大。
